## 建议顺序

先修下述两个已确认边界，再推进后面的产品改进；两项均为小范围修补，不需要重构执行链。

### 前置修补：错误证据丢失与恢复耗时失真

**A. P1：清理异常覆盖原始异常。** `src/app-server.js:250` 在 finally 中执行 `await client.stop()`；当执行先失败、stop 再抛错时，调用者只能收到清理异常，原始错误没有保留下来。`src/runtime.js:137` 仅持久化 error.message，进一步限制排障。成员和队长分别使用当前 CodexBackend.run 的内存客户端桩复现：初始化抛 `original protocol failure`，stop 抛 `cleanup exit unconfirmed`，最终仅有后者且 cause 为 undefined。尚未实测真实宿主的这组组合故障。

最小修补：同时保存主错误和清理错误，继续把退出未确认视为阻塞条件；不要为保留主错误而吞掉清理失败。验收新增双重失败回归，断言两项证据同时存在、退出未确认仍禁止重派；然后扩展下文的结构化错误元数据。

**B. P2：集成恢复覆盖已有执行结束时间。** `src/runtime.js:149` 已记录成员执行结束，集成使用单独时间；但 `src/store.js:49` 在 integrating 恢复时无条件重写 attempt.endedAt，`src/status.js:68` 据此计算成员执行耗时。当前 `tests/write.test.js:148` 覆盖崩溃后的终态、保留补丁与不重放，尚未断言原结束时间保留。

成员和队长分别用当前 TaskStore、内存 SQLite、文件系统桩与固定时钟复现：原始 00:00–00:01 共 60 秒，02:00 恢复后变成 7200 秒；原始 phase 仍为 integration_verification。顶层展示按终态正确显示 integration_failed，不能将这个问题描述成“仍显示执行中”。这不是磁盘崩溃或真实进程故障测试。

最小修补：保留已有 endedAt，另记恢复观察时间；没有真实结束证据时保持未知，不用重启时间代替。验收固定时钟下原 60 秒保持不变，恢复阶段不伪造精确结束时间，正常执行与集成统计保持原口径。

### 1. P1：明确目标工作区并检查调用目标

**性质：产品正确性防护缺口；没有发现本轮操作了错误仓库。**

证据：`src/plugin.js:70` 将配置快照写入包，`:72` 固定使用包内配置；`src/cli.js:76` 用配置中的 workspace 创建 runtime；`src/runtime.js:87` 将其作为无 worktree 成员的 cwd。`src/contracts.js:22` 的任务合同没有调用方期望目录，`src/status.js:101` 的 overview 也未返回目标 workspace。cwd 校验能证明宿主遵守配置，不能证明该配置就是当前聊天希望处理的项目。

触发场景：为项目 A 构建插件，在项目 B 的聊天调用同一缓存；用户可能误认为目标随聊天切换。

最小方案：overview、创建回执和启动反馈显示规范化目标目录；新增调用方期望目录的匹配检查，技能从当前工作区明确提供，目录不符在模型启动前失败。继续保持单工作区 owner，不必先实现动态多仓库调度；宿主不能提供目录时明确未知，不猜测。

验收：用两个临时仓库测试 A 匹配成功、B 不匹配且 backend 未调用；等价 symlink 路径通过；旧合同缺字段的兼容策略明确。新版 MCP 字段实施时再核对官方 SDK 文档与实际 schema。

### 2. P1：在成员启动前检查执行环境

**性质：已有边界的产品改进。**

证据：`src/runtime.js:81` 准备 Git 工作区后直接进入 `backend.run`，验证命令在 `:106` 才运行。Git 内容快照不等于完整依赖环境；历史 fixture 已发现 worktree 可向上解析源 node_modules，ignored 本地数据则不随快照复制。

最小方案：为显式执行计划增加有界、可审计的预检要求，确认命令可用、必要运行时和声明的依赖/文件条件；保存工具版本、锁文件摘要和实际依赖来源。只检查明确声明的输入，不扫描所有 ignored 内容，不打印环境变量值，不隐式安装。不要把“基线测试必须通过”作为通用条件，因为修 bug 的任务可能本就有失败测试。

验收：缺命令/依赖/声明文件时在 writer 前给出可定位原因；Git 干净但依赖来源不同能够显示差异；预检超时和取消确认进程退出；有意失败的业务断言不被误判成缺环境。

### 3. P1：补齐错误分类和恢复指引

**性质：排障与效率改进；已有阶段记录可直接复用。**

证据：`src/runtime.js:137` 将异常保存为 message 并在 signal aborted 时统一记 cancelled；`src/status.js:55` 的下一步主要按任务终态给出。环境错误、截止时间、用户取消、协议失败、审查拒绝和源 drift 需要不同处理。

最小方案：增加稳定错误码、失败阶段、原因、建议动作和是否允许显式重试的元数据，保留现有状态兼容与进程退出门禁。复用 phases、memberUsage、reviewerUsage 汇总耗时与用量；未知保持未知。恢复入口先提供只读诊断，不自动接管、重放或依据 PID 单独杀进程。

验收：受控 fixture 区分缺命令、超时、用户取消、协议异常、验收拒绝及集成冲突；错误属于当前 attempt；退出未确认仍拒绝重派；旧记录显示未知分类。

### 4. P2：用真实任务建立质量和效率对照

**性质：产品价值证据缺口。**

证据：`scripts/smoke-write-live.js:20` 的真实写 fixture 为 sum 修复，`:64` 明确不是 benchmark；当前目录中没有独立评测 runner。现有 smoke 足以说明闭环能运行，不能说明复杂任务更准确、更快或更省。

最小方案：先准备 5–10 个真实、边界明确的任务，覆盖定位、分析、单文件修复和跨文件修改；固定初始提交、模型能力、上下文、权限与验收，对比单强模型、原生子 Agent、此插件，OMX 后续加入。记录验收通过率、严重错误、总耗时、返工、人工介入和 host 用量；费用只在价格证据充分时计算。样本较少时不宣称统计优势或开启成本路由。

验收：同一任务可以重置重跑，失败样本保留，验收尽量独立于执行方案；输出逐任务数据与汇总。先交付 fixtures 和报告格式，付费批量运行单独取得授权。

### 5. P2：一键 build 的快速失败与自动回归

**性质：新增入口的工程加固；当前未证实打包结果错误。**

证据：`scripts/build.js:19` 先执行 npm ci，`:39` 才解析完整配置，`:48` 才进入输出目录检查；只有显式配置不存在提前检查。`tests/plugin.test.js:33` 和 `:103` 覆盖 pack/doctor，现有测试未直接执行 build 编排。STATUS.md 已记录真实首次及重复 build 成功，但人工 smoke 不能覆盖全部失败路径。

最小方案：依赖安装前尽可能检查已存在配置的 JSON、显式输出冲突等确定性条件；为安装、模型探测、配置复用、重复构建及失败退出添加受控命令 fixture。保留一条用户命令，避免为测试引入框架；失败留下的可诊断产物说明清楚。

验收：配置明显无效/输出已存在时不运行安装；已有配置不被覆盖；探测不支持 high 时无推理且明确失败；重复构建保留旧包；安装/探测失败不会输出成功提示。测试不访问真实账号、不联网安装依赖。

## 建议切分

- 下一小版本：先修上述两个边界并补针对性回归，再加目标工作区展示和匹配防护、build 回归。若希望进一步缩小范围，可把入口改进独立成后续补丁。
