# 实施路线

每阶段按准确率、完成效率、成本顺序验收。详细状态以 STATUS.md 为准。

## P0：只读委派闭环（当前）

- 中心思想和边界；显式任务合同、依赖与接受标准。
- 默认强模型；有配置的评测依据后才允许指定合格模型。
- 官方 App Server、新线程、只读沙箱、结构化结果。
- SQLite 任务/attempt 记录、唯一运行时、并发上限、取消和保守恢复。
- 官方 MCP SDK 暴露少量工具，CLI 提供诊断。
- 完成后进入 awaiting_review，由队长按验收条目核查后完成。
- 协议模拟、MCP 实际连接和本机握手验证；模型质量单独实测。

## P1：可修改代码的闭环

- 真实任务基线（含未提交改动处理）、独立 worktree、范围审计。
- 执行验收命令、存储日志与退出码、强模型审查、集成后验证。
- 按故障类别决定修复、强模型升级或补任务合同，保留新 attempt。
- crash/孤儿进程/迟到结果/合并冲突故障注入。
- 在以上能力齐备前，P0 对写任务直接拒绝。

## P2：证明质量与效率

- 真实代表性任务集，对照单强模型、原生子 Agent、OMX。
- 统计通过率、严重缺陷、总耗时、返工和人工介入，最后统计用量。
- 先给出结果，再决定需要哪些模型分层；没有评测不自动降低模型能力。

## P3：有证据的扩展

- 根据真实需求增加界面或其他后端；不预先铺大型框架。
- 桌面宿主唤醒、插件安装路径和通知机制分别实测。
- 若确需无人值守协调者，明确其权限、会话和与主聊天的职责边界。
