# 上一轮 Team 审查的效率与可靠性复盘

日期：2026-10-14。用户要求复盘上一轮项目 bug 审查，重点评价主子任务、实际提效和可靠性。依据宿主主线程回放、两项 Team 的持久记录、主 Agent 独立复现及当前实现，不重新启动成员或进行模型对照长跑。

## 判断

插件真实执行了并行成员，成员带来可核查的独立发现；本轮证明了并行探索与报告验收链路有价值。没有同条件单 Agent/原生子 Agent 基线，不能证明插件缩短了同等质量交付的总时间，更不能把三个成员发现等同于准确率提高 75%。

本轮的主要效率问题是：任务仍偏宽、最终报告较晚提交、只读验证能力与报告状态不匹配、需要主 Agent 从报告重建复现，以及前台等待和重复上下文消耗。我的主任务调度和报告收尾也有明显改进空间，不能全部归为插件运行时慢。

## blocked 的语义问题

工作区报告的三条 criteria 全为 satisfied=true，但 blockers 包含“只读合同不能创建真实 Git fixture”和“不能写 STATUS”。运行时在 src/runtime.js:214 根据非空 blockers 将任务置为 blocked，忠实执行当前规则；没有伪造成功。

然而本合同验收允许“源码或复现证据”，没有要求成员必须完成真实 Git 端到端验证；子任务明确保持只读，文档维护由主 Agent 完成即可。不能写 STATUS 不是本子合同未完成的理由。这里体现了两项问题：

1. 成员把验证限制和不属于自身交付的事项当成了阻塞条件，状态表达偏保守且不自洽。
2. 运行时的 result schema 没有把“导致某条验收不满足的 blocker”和“已完成报告的验证局限”明确分开，也没有检查 all-true criteria 与 blockers 的语义一致性。

不应简单忽略 blockers 或把 blocked 自动改成功。应让真正阻塞项关联具体未完成验收，将 limitations/未执行验证单独记录。只读分析的结论可以带局限进入 awaiting_review，再由队长决定是否补验。

## 哪些可靠，哪些还依赖队长

- **执行真实性有证据。** 两次 attempt 记录的线程、turn、PID 不同，实际模型/强度一致，开始和结束时间重叠，记录用量及成员退出确认。这不是主 Agent 代写两份成员报告。
- **合同和状态门禁本轮发挥作用。** 成员按 acceptance 返回结构化报告；正常报告 awaiting_review 后需显式 captain pass；含 blockers 的报告保留 blocked，没有静默升级为 succeeded。
- **语义正确性仍由主 Agent 负责。** src/runtime.js:258 仅在 executionPlan 存在时检查机器验证回执；本轮两个普通只读任务没有 executionPlan。review(pass) 是 captain-attested，代码不会独立证明文件行号或复现实验的事实。四项最终确认依赖主 Agent 实际复核，不是插件自行证明所有报告正确。
- **本轮未检验全部可靠性能力。** 没有真实写任务、独立 writer/reviewer、集成、重试或取消故障；不能以这次只读成功证明这些能力全部可靠。247/247 回归是另一组证据，不等同于本轮真实模型写闭环。
- **事后过程追溯有缺口。** 宿主 read_thread 能读主线程，但两项 App Server ephemeral 成员线程均返回 No Codex thread found。插件目前持久保存最终报告/usage/phase，src/app-server.js:236 起没有持久化通用 command/tool 事件。成员完整命令轨迹本轮无法通过该宿主读取，不能声称逐条重放过所有子任务工具；队长独立复现补强的是结论。
- **独立线程有边界。** 两成员均为同一 krill/gpt-6.1-sol/high；新会话和分工减少共享上下文，但相同模型仍可能有共同盲点。只读成员未创建独立 Git worktree，不构成文件系统隔离。

## 与不用插件的比较

- **单主 Agent：** 省去两次上下文建立、分工/等待/结果交接和部分复验重建；对已有上下文、范围窄的任务，预计更容易降低交付时间。本轮无法证明它能更快完成同样四项发现，不能利用已知答案进行事后速度宣称。
- **原生子 Agent：** 同样可以并行审查、提交发现、由主 Agent 验证。因此本轮三个额外发现主要证明多成员分工有价值，不能证明插件相对原生子 Agent 的独有优势。原生唤醒/线程读取可能更方便，但本轮没有在相同条件下实测速度与权限差异。
- **Team 插件：** 明确合同、项目归属、持久状态、显式验收和退出门禁是产品价值。对于长任务、跨轮恢复以及受控写入/集成更可能有优势；本轮仅实际验证了其中只读并行及报告验收部分。

以当前小项目、已有充分上下文、交付速度优先为条件，我会采用“主 Agent 先快速审查，再针对独立盲区派一个成员”的默认策略。用户要求全面审查、模块可独立推进时可用两个，但不应将建队视为默认提效保证。

## 下一轮最值得改变的事项

1. **先让子任务能交付可直接核查的证据。** 每个 finding 附当前行号、最小复现代码/只读命令、预期与实际输出、依赖和限制；只读纯函数复现不建真实 Git fixture，Git 复现由明确具备临时写权限的验证者完成。主 Agent 审查和复跑核心断言，无需从文字报告重新设计整套 fixture。
2. **缩小与调整分工。** 按具体问题面分工，例如“验证审计后到 reviewer/finish 的 deadline 窗口”“检查文件类型转换与 discard”，不要同时要求每个成员承担多个大模块的整轮升级分析。探索任务不可过早限定未知答案，但可限定模块和最大交付范围。
3. **修正 blocker/limitation 语义。** 不将全局 STATUS 维护等同于每个只读成员的交付要求；要求真正 blocker 指向未满足的合同 criterion，验证局限单独表达。
4. **降低观察与交接开销。** 有发现时先提供简短线索，完成后交结构化报告；主 Agent 有独立工作时继续执行，减少为填等待空档而重复探索。状态工具可提供版本游标/变化摘要，避免每次重复整份目标和派发元数据；不预设必须新建后台调度器或开放更多权限。
5. **做真正对照后再宣称提效。** 使用不曾曝光答案的同一批仓库快照/任务，固定模型、强度、工具权限、验收深度，随机执行顺序，比较单 Agent/原生子 Agent/插件。至少记录有效问题、严重误报、漏报、总交付时间、人工介入、主任务及成员总用量。把“发现”与“发现+复核+交付”分开测，避免主任务等待和收尾成本被隐藏。该评测本轮未执行。
