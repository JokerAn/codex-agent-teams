# 用户预期设想与当前实现偏差说明

**项目**：codex-agent-teams（Codex Agent Teams 插件）
**版本**：0.4.0 · HEAD `646f8f6`
**日期**：2026-10-13
**文档依据**：`UPGRADE-PLAN.md`

---

## 一、用户预期设想

用户希望的使用方式是——**在开始一次项目修改时，把团队插件当作开工的第一步**：

1. **队长先评估**这次改动到底是什么、涉及哪些部分、哪些部分互相依赖；
2. **队长决定开几个成员**，每个成员负责哪一块；
3. **每个成员按任务难度采用不同推理强度**（难的用强模型高强度，简单的用轻量模型）；
4. **多个子任务同时开工**，多个成员并行修改同一个项目；
5. **队长自己也承担一块工作**，而不是只站在旁边调度和验收；
6. 最终目标：**缩短从需求到正确交付的总耗时**，也就是真正的提效。

用户明确表示：**"让用户选 agent"这一步可以省略**，由队长先指定即可；重点是**尽快让多个子任务开工**。

---

## 二、现在的代码实际是什么

### 队长—成员—验收骨架：**扎实，没问题**

当前实现已经具备：

- **队长角色**：由当前 Codex 会话担任，负责目标、分工和关键判断（`PRINCIPLES.md`、`skills/team/SKILL.md`）；
- **成员执行**：通过官方 App Server 启动独立线程，每个成员有独立 worktree 隔离；
- **验证闭环**：命令验证 + 独立专家审查 + 队长逐项复核 + 显式集成 + 源工作区复验；
- **状态可感知**：每个工具调用返回双 content block（原始 JSON + 人类可读回执），**已在真实宿主中确认透传**；
- **多项正确性保障**：超时与取消区分、退出确认门禁、崩溃不重放、真实 Git 基线。

**这部分做得好，不该推倒重来。**

### 但开工方式与用户预期不一致

| 用户预期 | 现在的代码实际行为 | 证据 |
|---|---|---|
| **多个成员并行改同一项目** | **写任务完全独占**。只要有一个工作区绑定任务在跑，**任何新任务都不能启动**，连只读分析也不行 | `runtime.js:81` |
| 队长决定开几个成员 | 有上限（默认 2、上限 4），**但技能文档没规定"如何决定人数"** | `contracts.js:13`；`skills/team/SKILL.md` |
| 每任务不同推理强度 | **合同里没有 `model` / `effort` 字段**，只能在 expert/simple 两档预设之间路由 | `contracts.js:29`；`policy.js` `selectProfile` |
| 队长自己也改一块 | **受限**：队长改了源工作区，成员集成时会被拒绝 | `runtime.js:280` |
| 用户选 agent（可省） | 省略这一项**反而变成了启动门槛**：没有有效确认就无法启动成员 | `src/mcp.js` `teams_start` |

## 三、偏差清单

### 偏差一（核心）：多成员无法并行修改同一项目

**预期**：三个写成员同时开工，各自改各自负责的模块。

**现状**：`runtime.js:81` 一行判断决定两件事——

```js
if ((task.executionPlan && this.active.size) || [...this.active.values()].some(entry => entry.workspaceBound))
  throw new Error('Verified-worktree tasks run exclusively until member and command exit');
```

写任务必然带 `executionPlan` → **必然独占**。`maxConcurrency`（默认 2、上限 4）在写任务路径上**形同虚设**。

**偏差性质**：**核心能力缺失**。这正是用户所说"团队插件核心价值"的部分。

### 偏差二：即使放开独占，第二个成员的工作仍无法落地

这是**更深一层的结构性阻塞**，需要单独说明：

`workspace.js:234` 有一道检查：

```js
if (actual.head !== record.baseline.head || actual.indexDigest !== record.baseline.indexDigest
    || this.captureTree(this.root, actual.head) !== candidate.tree)
  throw new Error('Integration content or index differs; changes retained for recovery');
```

`captureTree` 返回的是**整棵源工作树**，而 `candidate.tree` 是**该成员自己的增量树**。第一个成员集成成功后，源工作树已经变化，第二个成员的这两棵树**必然不相等**——**跟两个成员改的文件是否相交毫无关系**。

已实测复现（两个改不相交文件的成员）：

```
candidate.tree (基线 + 第二个成员的改动)   = a121cbf75805e50523952f32e1ba634120758016
captureTree(当前源工作树)                  = 4ee2462c336faad285e358b4338b0061381aaa54
=> 不相等，第二个成员被拒
```

**偏差性质**：**结构性阻塞**。所以"回到主线"**不是删一行判断**，而是一次需要仔细设计、且必须重跑证据链的改造。

### 偏差三：无法为单个任务指定模型与推理强度

**预期**：这个成员用强模型高强度改接口，那个成员用轻量模型补测试。

**现状**：合同顶层只有 `profile: auto | expert | simple | qualified`，**没有逐任务的 `model` / `effort`**。"推理程度有高有低"当前**无法表达**。

**偏差性质**：**能力缺失，但与并行无关**——补起来便宜，是独立的、可以立刻兑现的一项。

### 偏差四：技能文档没有"先评估、再决定人数"的流程

**现状**：`skills/team/SKILL.md` 共 65 行三节（何时委派 / 最小合同 / 汇报什么），**没有把"评估需求 → 决定人数 → 分配职责与强度 → 并行启动 → 队长继续承担独立工作"规定为默认流程**。

### 偏差五：可省略的模型选择，变成了启动门槛

用户的预期是"用户选 agent 可以省，队长先指定"。现状是**没有有效确认就无法启动成员**。

需要说明的是：**这项不是无缘无故加的**——它来自此前一轮明确的需求（用户确认模型分工，避免静默降级）。按现在的方向，它应当是**用户可选的控制项**，而不是团队启动的必经步骤。

## 四、偏差的根因：不在代码，在原则文档

**这是本次诊断最重要的结论。**

`PRINCIPLES.md:7` 白纸黑字写着：

> 这里的效率指从需求到正确交付的总耗时与用户投入，**不是单次模型响应速度，也不是并行成员数量**。

**项目主动把"并行成员数"从效率定义里剔除了。** 后续所有代码都忠实执行了这条原则——把力气投在"把单个任务做可靠"上。

所以这不是实现跑偏，而是：**代码没有背叛原则，是原则与用户目标不一致。**

**这一点决定了改造顺序**：**不先修这条原则的表述，后续任何并行改动都会被再次判为"偏离设计"。**

---

## 五、升级改造方案（按 `UPGRADE-PLAN.md`）

### 第 1 步：修正原则文档对"并行"的表述

- **做什么**：修改 `PRINCIPLES.md:7`，把"效率不是并行成员数量"改为能容纳并行的表述（效率仍是总耗时，但**并行是实现总耗时目标的手段之一**）。
- **为什么先做**：不修它，后面每一步并行改造都会与项目自己的原则相冲突。
- **成本**：极低。
- **验证**：文档改动；确认与 `docs/ROADMAP.md` 的表述一致。

### 第 2 步：跑一次真实项目修改，量出协调开销（**关键前置**）

- **做什么**：用本插件真实完成一次中等复杂度的项目修改，记录三个数字：**队长拆任务耗时 / 成员等待耗时 / 复核耗时**。
- **为什么必须先做**：**"多成员是否真的比单模型更快"至今没有任何数据。** 仓库有 42 个定义用例，实际只跑过 3 个，而且已标注过期；同条件效率对照（单强模型 vs 原生子 Agent vs 本插件）**从未做过**。
- **在无数据的情况下投入并行写机制，等于给一个未验证的假设加杠杆。** 而且"拆分 + 协调 + 复核"的开销可能吃光并行收益——这正是用户自己点到的顾虑。
- **验收标准**：拿到真实的耗时分布。若瓶颈确为"队长排队等成员"，则并行改造有依据；若不是，则第 4 步应重新评估优先级。

### 第 3 步：给合同加逐任务 `model` / `effort` 覆盖（**可与第 2 步并行推进**）

- **做什么**：`contracts.js` 增加可选的逐任务 `model` 与 `effort`；`policy.js` 的 `selectProfile` 支持该覆盖，并复用 `models.js` 的既有校验，确保不可用的模型或不支持的强度在推理前被拒。
- **必须守住的约束**：
  - 不静默降级（覆盖必须是队长**显式**指定）；
  - 重试规则保持——"被拒绝的廉价运行不得静默重复在更便宜的路径上"；
  - 覆盖要记录进 attempt 作为证据，并在状态里可见。
- **为什么现在做**：**便宜、独立于并行、立刻兑现用户"推理程度有高有低"的需求。**
- **成本**：小（单文件为主）。

### 第 4 步：视第 2 步数据，决定是否做并行写改造

若数据支持，按两阶段推进：

- **阶段一**：放开 `runtime.js:81` 的 `workspaceBound` 全进程排他，保留 `maxConcurrency` 容量门 → **多个写成员可以同时在自己的 worktree 里干活**（推理是真正的墙钟大头）。
  **诚实代价**：此阶段第二个写者**仍无法落地**。不先解决下面的阶段二，"并行开工"只是让第二个成员**白干得更快**。
- **阶段二（核心）**：把 `workspace.js:234` 的证明从"整棵源树 === 我的增量树"改为**按补丁触及路径的落地证明**——收窄到补丁涉及的路径必须等于 post-image，且确认没有其他路径发生变化。**这道证明仍然拦得住静默三路合并。**
  **连带必须重跑的证据（不可省）**：命令验证、独立专家审查、队长复核。因为"某成员的改动 + 当前源"这个组合**从未被执行过**，沿用旧 receipt 是虚构证据。**但成员推理不重跑**——代码成果保留，只重跑确定性检查。

### 第 5 步：产物与文档卫生（独立小项，随时可做）

- 清理 `dist/` 旧副本（现有 **12 个目录、约 191MB**；**删除需用户显式授权**）；
- 统一两个 plugin manifest；
- `mcp.json` 的 `env.PATH` 脱敏（当前是完整宿主环境快照）。

## 六、改造后的验收标准

改造完成后，应当能验证以下场景：

1. **两个写成员改不相交文件** → 两者**都能成功集成**，源工作区最终包含两处改动；
2. **两个写成员改同一处** → 后者被**明确拒绝**，且**源工作区不被改动**，错误信息说明原因与下一步；
3. **队长在成员运行期间修改源工作区** → 行为明确（要么被允许并有冲突处理，要么给出可操作的提示）；
4. **逐任务指定模型与强度** → 成员实际使用指定的模型与强度，且记录在 attempt 证据里；
5. **协调开销有数据** → 相比单强模型，总耗时确实下降，或明确说明未下降及原因。

## 七、边界与不做的事

**不削弱的安全保证**（改造中必须保留）：

- 每个写成员独立 worktree 隔离；
- 命令验证 + 独立专家审查 + 队长逐项复核；
- 退出确认门禁；**进程未确认退出时不得重派同一任务**；
- **崩溃后不自动重放**；
- **不把未验证的结果标为 succeeded**。

**明确不做的事**：

- **不删除** `workspace.js:234` 的落地证明（只收窄其粒度）；
- **不引入**完整的 Git 合并/冲突解决引擎（当前阶段不需要）；
- **不加** `git apply --no-3way`（实测不改变任何 `--check` 结果，只会让行为依赖 git 版本）；
- **不把**"并行成员数"本身当作验收指标——验收指标是**总交付耗时**。

## 八、当前状态与已知阻塞

**已完成**：原两条痛点（感知低、委派重）已基本解决，且拿到了真实宿主证据——工具回执的第二块内容**确认被宿主透传**。本机回归 **182/182 通过**。四项状态一致性缺陷已修复（含两个由上一批引入的回归）。

**跑真实任务前必须先解决**（否则成员起不来）：

1. 状态库的模型分工偏好**为空** → 启动成员时会被拒绝；
2. 当前宿主里模型确认表单返回 `decline`（外层 `approval_policy` 导致，**不是用户点了拒绝**）；
3. 状态库**单 owner**，MCP server 持锁期间终端无法并行操作。

**解锁路径**：关闭 Codex 会话释放 owner → 在独立终端交互确认一次并选择**记住此工作区分工** → 重开 Codex，之后自动复用。

**未验证的边界**：本轮改动**只跑过离线单测**，未跑真实模型任务；同条件效率对照未做；桌面 UI 操作与跨平台矩阵未验证。这些**不能声称已完成**。

---

## 九、给用户的一句话总结

**队长—成员—验收的骨架已经扎实，问题出在"多个成员不能同时改同一个项目"，而且真正卡住它的是一道结构性检查（不是表面那行独占判断）。**

**改造顺序的关键是：先改原则文档，再拿真实数据，最后才动并行机制**——因为"多成员是否更快"目前没有任何数据支撑，盲目投入等于给未验证的假设加杠杆。

**在此之前，有一件便宜且立刻兑现的事可以先做：让每个任务能单独指定模型与推理强度。**
