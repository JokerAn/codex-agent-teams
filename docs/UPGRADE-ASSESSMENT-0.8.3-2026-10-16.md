## P1：更新事务缺少跨进程互斥，回滚会撤销另一进程的成功结果

位置：`scripts/update.js:125–140`、`:155–175`、`:183–195`。

证据链：A 读取 0.8.2 状态并安装 0.8.3 → B 从同一 Codex home 完成 0.8.4 更新并返回成功 → A 最后检查发现 marketplace 来源变化 → A 的 catch 删除当前插件并恢复自己最初读取的 0.8.2。当前只有项目运行状态检查，没有覆盖共享 home 的更新事务所有权。

本轮官方 CLI / 两个 Node 进程、受控调度复现：B 返回 0.8.4，最终官方列表为 0.8.2，B 的成功安装目录已被删除。这是已确认的并发正确性缺陷，影响共享 home 的更新进程，不限同一项目；未测随机发生概率。

建议列为下一修补版第一项：按规范化后的有效 `CODEX_HOME` 和 marketplace 获取排他锁，在读取旧安装状态前持有，覆盖修改、验收和回滚；锁包含所有者身份，释放和过期恢复核对所有权。回滚前再核对当前状态仍属于本次更新，避免删除外部 CLI 等不遵循锁的操作结果。可使用原子文件系统锁，保持现有小型项目结构。

验收：两个真实更新进程共享 home，后者应在修改前等待或明确拒绝；成功更新的缓存不能被前者删除。补锁争用、异常退出、所有权变化和恢复失败用例。

## P2：安装边界需要重新验证模式和版本语义

位置：`src/plugin-package.js:72–82`；`scripts/update.js:42–63`、`:120–124`、`:168–179`。

证据链一：`pluginTarget` 透传未知 `build.mode` → `installationIdentity` 仅对精确的 `native` 执行四文件清单 → `native-typo` 加空 `src/` 被当成严格包检查 → 官方 CLI 安装额外 `extra-runtime.js`，更新器返回成功。没有证据表明额外文件被自动执行。

证据链二：候选 manifest 版本被改为 99.0.0，package/build-info 仍为 0.8.3 → 更新器仅比较后两者 → 官方 CLI 按 manifest 安装至 99.0.0 → 缓存与损坏候选字节相符 → 更新器返回 0.8.3。本轮重新断言了官方列表与成功回执的版本矛盾。

两例都需要构建后的候选被修改或直接传入异常 prepared package。干净 builder 已有 metadata 校验，因此不能将它们描述为正常构建必然产生错误包。

建议同批修复：将无依赖的候选语义校验共用于构建和安装，显式枚举 `native/strict`，未知模式在任何安装修改前拒绝；核对 manifest/package/build-info 的名称、版本及资源声明，并对 native 按既有构建算法重新计算 `sourceDigest`。安装后同时核对官方回执/列表和实际缓存身份，保证报告的版本一致。历史包缺少身份时保留显式迁移边界。

验收：两类异常候选均预检失败且 home 零修改；补已安装缓存语义异常及正确 native、strict→native 回归。

## P2：恢复来源需要可验证的不可变备份

位置：`scripts/update.js:140–167`、`:186–195`。

证据链：旧缓存只保留身份摘要 → 最后一次检查旧来源 → 删除旧缓存 → 新安装失败，同时旧 marketplace 的 skill 被修改 → 回装读取可变旧来源 → 安装漂移内容后才发现与原摘要不符。

本轮官方 CLI 复现确认原旧字节丢失、漂移后的 skill 已回装。代码明确报告“恢复未完成”，所以它属于恢复能力缺口，不属于把恢复失败报成成功。

建议与更新事务一起补强：删除旧缓存前准备可验证备份或临时恢复 marketplace，恢复所用内容在回装前再次核对；恢复成功后核对缓存，按事务结果清理备份。跨进程锁只能约束配合本项目的更新器，不能独自消除来源被外部改写的窗口。

验收：在“最后预检通过、旧缓存已删、新安装失败”的时间点修改旧来源，仍能恢复原字节；备份损坏时在回装前明确失败。strict 依赖未逐文件核对需继续明示，不能用关键文件恢复推断所有依赖字节恢复。

## P2：中文或空格目录下的测试路径处理需要修复

位置：`tests/config.test.js:39–41`。

证据链：`new URL(...).pathname` 生成编码路径 → 直接作为 Node CLI 文件参数 → 中文目录被解释为字面 `%E5...` 路径 → `MODULE_NOT_FOUND`。

本轮 `node --test --test-reporter=tap tests/native-plugin.test.js tests/config.test.js`：13 项、12 通过、1 失败、0 cancelled/skipped；失败正是上述配置 CLI 测试。既有同 HEAD 的全量覆盖率证据为 412 项、411 通过、1 失败。产品 CLI 在正确解码路径下的中文/空格目录检查已有独立通过证据，因此这是测试入口缺陷。

建议使用 `fileURLToPath`，检查其他把 URL pathname 当本机路径的测试入口，增加源码 checkout 位于中文与空格父目录的回归。验收时保留原 checkout，不依赖改目录绕过失败。

## P2：最低 Node 版本的 CI 需要独立处理两类失败

Ubuntu：日志显示 411 项测试通过、0 失败，但 coverage 报 `Unexpected end of JSON input` 并 exit 1。此证据不足以确定具体损坏文件的生产进程。2026-10-17 复核确认：Darwin 专属测试使 macOS 比 Linux 多注册 1 项，因此 Ubuntu 的 411 项并非漏执行；该 job 的失败来自 coverage 报告。建议分开功能测试与 coverage 报告，保留原始 coverage 产物并定位缺失/不完整记录；矩阵继续覆盖声明的最低版本。若最终调整最低 Node 版本，应同步 engines、文档和 CI，并给出兼容性依据。

验收：同一修复提交的四组远程矩阵都提供完整测试计数；coverage 单独成功产出且失败不会被忽略。
