## 一、先达到什么效果

产品目标：队长能决定是否委派、成员交付便于验证的证据、运行时如实表达完成程度；最终以同等质量下的总交付时间衡量效率。已有合同、唯一 owner、退出确认、独立审查、显式集成与源复验继续作为基础。

| 目标 | 用户能感受到的效果 | 验收标准 |
| --- | --- | --- |
| G1 正确性 | 正常文件/目录转换可完成；超时不再继续启动审查；状态与模型约束一致 | A1～A4 的触发用例全部修复，既有回归保持通过，symlink/越界/源 HEAD/index/退出门禁不退步 |
| G2 报告可直接复核 | 队长取得源码证据或最小复现后即可检查，减少从文字重新设计实验 | 每个确认 finding 都有位置、触发条件、预期/实际、证据类型和验证边界；需要复现的结论提供可审阅步骤/代码；不将未运行脚本标成实测 |
| G3 完成状态清楚 | “报告已完成但有验证局限”可进入队长复核，真正缺少必要证据才阻塞 | all-true criteria + limitations → awaiting_review；真实未满足 criterion → blocked；all-true + blockers 等矛盾报告明确结构诊断，不自动成功、不自动付费重试 |
| G4 过程可追溯、观察轻量 | 可看到最近可核查动作及命令是否结束，重复等待不反复灌入整份任务 | attempt 内有有界工具/命令摘要；无变化的增量等待响应目标不超过 1 KiB；旧客户端/面板保持可用；缺失数据明确标未知 |
| G5 有证据提效 | 同等准确率与验收深度下，总交付更快，或能清楚说明该任务适合直接做 | 采集主任务全时长、成员时长、交接复核时长及完整用量；小样本对照达到质量门槛才比较时间。初始优化目标为可比任务的成员结束后交付尾部中位数缩短至少 30%，这是待验证目标，不是收益承诺 |

G1～G4 可以用离线/受控协议和无推理宿主测试验证工程行为；G5 需要真实任务对照，不能用模拟、token 减少或成员并行时间代替。上一轮尾部 292.1 秒只是问题定位样本，不用已曝光答案的同一任务证明速度提高。

## 二、升级方向

1. **先收口当前正确性。** 修复已复现的边界，保持小补丁，不改变写任务的保守交付机制。
2. **把交付物从长篇发现说明升级为可复核证据。** 保留主 Agent 的独立判断，减少重复搭建 fixture 与重复探索。
3. **把报告局限与真正受阻分开。** 调整合同、提示、运行时校验和状态显示，而非放松成功门槛。
4. **以有界观察代替反复全文回执。** 增加必要的动作元数据和变化摘要，不扩展为后台队长或完整终端录制。
5. **按任务决定成员数，再实测交付收益。** 有现成上下文的小任务优先直接完成；可分离的独立部分才派 1～2 个成员，不把人数当目标，不静默降级模型。

## 三、实施分三批

### 批次 A：四项正确性修补

先做 A2/A4，再收口 A1/A3；完成后可以独立交付，不等待后续产品能力。

| 项目 | 最小改法 | 重点验收 |
| --- | --- | --- |
| A2 deadline | reviewer 调用前、成功 finish 前补绝对 deadline/取消检查 | 两次 candidateEvidence 超时窗口；前者 reviewer 调用为 0，后者 timed_out；取消先发生仍归 cancelled |
| A4 路径转换 | 清单区分旧 Git 文件已删除、普通目录占位、普通文件父路径引起的 ENOTDIR；新增路径继续审计 | 双向文件/目录转换的 source snapshot、成员 staged/unstaged、candidate、集成/源复验与 discard；symlink/特殊文件/范围外改动仍拒绝；HEAD/index/用户内容保持 |
| A1 状态一致 | 提取基于完整 snapshot/owner 的单任务观察规则，MCP compact 与 overview 共用 | owner 缺失/退出/存活、endedAt、integrating；两入口耗时/指引一致，观察不获取 owner 或恢复任务 |
| A3 review 路由 | 对最终 review selection 统一约束 expert model/effort，非匹配明确拒绝 | auto/expert/simple/qualified/显式 model/重试；非法选择在 attempt/backend 前拒绝；正常 legacy 非 review 不退步 |

主要文件：src/runtime.js、workspace.js、status.js、mcp.js、policy.js 及对应测试。没有新增依赖。先跑各自故障回归，再跑完整套件；247 是当前基线测试数，新增后按真实数量报告。受控模型与真实本机 Git/命令证据分别记录。

### 批次 B：把报告与验收的交接做完整

这一批针对上一轮最直接的交接浪费，优先于更复杂的调度。

**B1 合同先说明验证边界。** team skill 的分工必须同时说明“成员交付什么”和“谁能执行哪类验证”。只读分析允许静态证据/无外部写入的受控实验；需要临时 Git 写入的验证由主 Agent 或另行声明能力的验证步骤完成。主 Agent 统一更新 STATUS，禁止将全局记录要求变成每个只读成员的额外交付项。不为完成 fixture 自动扩大成员权限。

**B2 固定 finding 的证据格式。** 第一版沿用 findings/criteria.evidence 的现有格式，先用提示和示例要求以下内容，不立即引入第二套发现对象协议：位置、触发条件、预期、实际、最小步骤/代码、实际执行者与未验证边界。静态即可证明的问题允许仅提供源码证据；命令输出必须区分成员自述、运行时回执、队长独立验证。队长审阅命令再执行，不自动运行成员提供的代码。

**B3 结果增加验证局限并检查一致性。** 在现有结果中增加可选且有长度上限的 limitations；旧报告没有此字段时按空值读取，blockers 保留现有类型，避免历史记录批量改写。真正的 blocker 必须在未满足 criterion 的 evidence 中说明对应影响；all-true criteria 却含 blockers 等矛盾结果输出明确的结果校验诊断，不改成成功。所有 criterion 满足、没有 blocker、仅有 limitations 的分析报告进入 awaiting_review。队长仍逐项验收；写任务原有机器验证、独立审查和集成门禁保持。

**B4 兼容与验收。** 更新 result schema、outputSchema、validateResult、runtime/status、skill 及示例，测试旧结果读取、新报告生成、真实 blocker、局限报告、矛盾报告、CLI/MCP 展示；不让旧 blocked 自动翻转，不为报告矛盾自动调用模型重试。公开协议实现时核对官方 SDK/本机 schema；本轮没有修改接口。

### 批次 C：轻量过程证据与增量观察

**C1 有界动作摘要。** 仅处理本机 App Server 官方 schema 确认的工具/命令事件，记录 item ID、动作类型、已确认 cwd、起止时间、退出码及限长摘要。字段不存在就标未知，不从自然语言猜测执行事实。默认不保存完整参数、环境、stdout/stderr、模型思维或整份协议帧；避免记录敏感参数和持续大输出。第一版建议每 attempt 最多 100 条、每条最多 512 字节、总上限 64 KiB，超限明确 truncated；这些是实现上限草案，需要测试按字节核实。

写入继续由运行时拥有，绑定当前 task/attempt，迟到事件不得改写新 attempt。动作摘要是观察证据，不作为测试通过或文件未变的机器验收依据。它改善定位能力，不宣称能够完整回放子线程。

**C2 增量 status/wait。** 在现有工具上增加可选游标/记录版本，不增加新工具。首次返回足够完整的快照；之后无变化只返回 task/attempt、记录版本、phase/status、更新时间和 unchanged。有变化返回受限的变更摘要；verbose 保持显式获取原始记录的入口。游标绑定项目/任务/attempt，错误或重连失效时明确要求完整快照，不返回错误项目数据。兼容现有无游标客户端和实时面板。

**C3 队长工作流。** 主 Agent 有独立工作时继续执行，定期观察与关键阶段反馈遵守现有前台约定；无新记录时用一句准确回执，不用重复探索填满等待。仍用有界前台等待，保留连接关闭清理；不预设宿主提供不存在的自动唤醒。实现前先检查 SDK/宿主能力，不以新增后台服务绕过限制。

**C4 验收。** 覆盖未知/部分事件、重复与迟到 item、多字节截断、关闭期间事件、命令失败/未退出、旧宿主无字段、跨项目游标、重连、无变化响应大小和面板刷新。先用受控事件，再用无推理宿主能力核查；真实成员验收另列，未跑则明确记录。

主要文件：src/app-server.js、runtime.js、store.js、status.js、mcp.js、skills/team/SKILL.md 及对应测试。优先复用既有状态存储，不新增常驻服务、框架或通用录制子系统。

## 四、开发怎样组织，避免再次把协调变成瓶颈

| 工作 | 主 Agent | 成员使用方式 |
| --- | --- | --- |
| 批次 A | 直接实施互相关联的小补丁，保护主目录/index | 实现结束后，按风险安排一个范围明确的独立审查；不边改同一基线边让成员评审 |
| 批次 B | 负责 schema/runtime/status 的一致性及向后兼容 | 存在独立测试矩阵设计任务时才派只读成员；不强制两成员，不重复整仓库探索 |
| 批次 C | 负责协议核查、事件归属和最终集成验证 | 可把已冻结接口下的协议/容量审查作为独立只读任务；同项目写任务保持现有独占 |
| 每批收尾 | 核对原合同、独立复跑关键证据、统一更新状态和交付文档 | 成员自述不直接变成功；不新建“只为证明插件参与”的任务 |

每个实现批次开始前核对交付目录和用户已有改动，代码停止修改后先通知用户再验证。定向检查通过后做该批必要完整回归；没有新变更不重复全量。完成一个批次即可交付，避免把 A 的小修补拖入 C 的协议开发。

## 五、如何证明真的提效

先用离线/受控测试测回执字节、事件容量和重复元数据；这些只能证明工程开销改善。真实评测计划采用未曝光答案的两个初始任务（审查类、修改类各一），每项比较单强模型、原生子 Agent、Team，保持模型/强度、仓库基线、工具权限、验收深度可比，新会话并随机安排顺序。

这是小样本机制验证，不作普遍速度结论。跨方案每次运行约束和上下文差异必须公开；原生方案权限不等价时不得硬算加速比。真实模型运行与预算需单独明确授权，本轮方案不启动这组评测或长跑。

记录范围：

- 正确性：有效发现/通过的修改、严重误报、已知验收漏项、必要验证是否完成；质量不满足的方案不参与“更快交付”宣称。
- 时间：需求到最终交付、成员运行、报告到队长验收、最终整合；总时长由宿主/评测器采集，不能用插件只掌握的成员时间替代。
- 返工：重写 fixture、重试、重新派发、源冲突、人工干预。
- 用量：主任务与成员全部 input/cached/output，未知保持未知；有实际价格才计算费用。

交付尾部中位数减少至少 30%作为优化目标；插件相对单 Agent/原生方案的总时长优势必须实测再报告。未达到就继续默认直接做/缩小委派范围，保留已经验证的可靠性收益，不追加并发数掩盖结果。

## 六、后置事项与交付边界
